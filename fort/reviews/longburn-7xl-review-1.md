## VERDICT: request_changes

The decision is correct, and I confirmed it with numbers rather than taking the doc's word for it. Against live Horizons vectors, `astronomy-engine` lands Earth and Moon within ~750 km and Mars within ~1980 km heliocentric — 0.1–0.3% of the relevant sphere-of-influence radii. For a patched-conic Tier 0 that is not close to marginal, and the alternatives are rejected on real grounds, not vibes. The tier fence holds, the acceptance gate is framed exactly right (thresholds pushed to `din.1`, "a provider failure is a test failure, not a reason to relax the fixture"), and rejecting runtime Horizons calls is the right instinct for replayability.

Two defects keep it from an approve, and both live in the text rather than the choice. The doc specifies six Horizons parameters precisely and omits the seventh — the timescale — which is the one that will make `din.1`'s fixtures disagree. And it states a fact about the library that is false, which I verified is false. This is a document; the text is the entire deliverable, and it becomes the record `din.1` implements against. Both fixes are a few lines. Nothing about the decision needs rework.

## Findings

1. **Line 11 + lines 27-34 — blocker. The timescale is unspecified, and stated wrongly.** The doc says the module will pass "an explicit simulation instant expressed as UTC days since J2000." `astronomy-engine`'s `MakeTime(number)` treats that number as **UT**, then converts internally to **TT** through a delta-T model (I measured TT−UT = 74.23 s at the sample epoch). Horizons `VECTORS` epochs are **TDB** by default. The fixture recipe on lines 27-34 pins targets, center, reference plane, corrections and output — but never the epoch scale, so a literal implementation bakes in a ~74-second offset. Measured cost of getting this wrong: Earth error goes 750 km → 1520 km, Mars 1982 km → 3059 km. The danger is not the magnitude; both still pass any sane gate. The danger is misdiagnosis. `din.1` sees roughly double the expected error, reads it as the library missing the accuracy bar, and triggers this doc's own line 49 upgrade path toward SPICE or precomputed tables for a reason that is actually a units bug. Fix: state the timescale the adapter accepts, pin Horizons' epoch scale in the fixture settings, and require the UT↔TT↔TDB convention to be documented at the adapter boundary.

2. **Line 13 — blocker. The Sun rationale asserts a distinction that does not exist.** The doc says "The Sun state is deliberately queried rather than assumed to be zero... That distinction is small for Tier 0 but keeps the provider's contract honest." I ran it: `HelioState(Body.Sun, t)` returns exactly `(0, 0, 0, 0, 0, 0)`. Querying the Sun *is* assuming zero — the Sun is the origin of the heliocentric frame by construction. The Sun's real displacement is only reachable via `BaryState(Body.Sun, t)`, which I measured at 0.0081 AU (~1.2 million km, larger than the Sun's own radius). The returned value is correct and the implementation is unaffected, so this is a defect in the record, not in the decision. But an implementer reading line 13 may believe solar barycentric motion is being captured when nothing captures it. Fix: either delete the paragraph or say plainly that the heliocentric Sun state is the zero vector by definition, and that barycentric motion is out of scope for Tier 0.

3. **Line 36 — should-fix. The determinism clause is too weak to catch this library's actual hazards.** "Prove byte-for-byte equal results for repeated calls with the same input" passes trivially while two real replay-breakers go undetected, both of which I confirmed:
   - `SetDeltaTFunction()` mutates a module-level `let DeltaT` (esm/astronomy.js:1131). Swapping the default `DeltaT_EspenakMeeus` for `DeltaT_JplHorizons` changes Mars output. It is process-global, so any code anywhere in the process can silently move every historical replay.
   - `cache_e_tilt` (esm/astronomy.js:1349) is keyed by **tolerance**, not equality: it reuses a cached value when `|Δtt| ≤ 1e-6` days (~86 ms). So the same input can return a value computed for a *different* instant depending on call history. Demonstrated: `Rotation_EQJ_EQD(t)` returns different values (~1e-15) in a cold process versus one warmed at t+43 ms. Repeated identical calls cannot see this — only differing call *history* can. This is the same shape as finding 2 of the 8b5 review: intra-process self-comparison proving purity rather than stability.
   - Verified good news, and it is the reason this is should-fix rather than blocker: the path the doc actually selects is clean. `HelioState` for Sun/Earth/Moon/Mars was byte-identical across 200 repeats, unchanged when interleaved with a `Pluto` call, and unchanged cold-versus-warmed. The hazard is one API call away, not in the chosen path.
   - Fix for `din.1`: assert the delta-T function explicitly at adapter init rather than inheriting the default; make the determinism test vary call order and history, not just repeat one call; keep the adapter on `HelioState`/EQJ and treat the of-date rotation APIs as off-limits without re-testing.

4. **Line 21 — should-fix. The ±1 arcminute figure is the wrong yardstick to hand the implementation bead.** It is an angular apparent-position claim, and at 1 AU it corresponds to roughly 43,500 km. Adopted as a threshold it would be uselessly loose — wide enough to hide a real regression. The actual measured heliocentric state error is 20-50x better than that. The doc is properly hedged ("subject to the project-specific validation gate below"), so this is not wrong, just unhelpful. Recommend recording the measured Horizons deltas in the doc so `din.1` starts its threshold proposal from evidence instead of from a marketing number.

5. **Nit.** `Pluto` is the one body in this library backed by a cached gravity integration rather than a closed-form series. Correctly irrelevant here, since the doc scopes to four bodies, but worth a line so a later bead does not casually add outer planets and inherit a different determinism profile.

## What I verified, and what held

Every factual claim in the doc that I could check independently held up except finding 2:

- `astronomy-engine@2.1.19` exists on npm, MIT licensed, is the current latest. Ships `esm/`, bundled `astronomy.d.ts`, and browser builds — the "no native build, no WASM boundary, no kernel loader" argument is accurate.
- `HelioState` genuinely supports all four required bodies including the Moon heliocentrically, which is the non-obvious one and the reason the VSOP87/Meeus DIY option is correctly rejected.
- "About 116 KB minified" — browser min is 113 KB. "DE440s alone is 31 MB" — `Content-Length: 32,726,016`. Both honest.
- The fixture recipe works as written. My Horizons query using the doc's exact settings (`CENTER='500@10'`, `REF_PLANE='FRAME'`, `VEC_CORR='NONE'`, `VEC_TABLE='2'`) matched the adapter's frame to ~1e-5 AU, which independently confirms the EQJ↔ICRF alignment claim. A frame error would have shown up as ~0.4 AU, not 1000 km. Modulo finding 1, `din.1` can execute this recipe directly.
- Accuracy, measured with correct timescale alignment: Earth 750 km, Moon 760 km, Mars 1982 km position; ~1.3 m/s velocity. Against SOI radii of Earth ~924,000 km and Mars ~577,000 km, that is 0.1–0.3%. Even against the Moon's much smaller ~66,000 km SOI it is ~1.2%. The choice is sound with real margin.

Charter compliance: **Standing order 10/11** — passing a numeric J2000 day value with no `Date` construction is the right shape, and the doc is explicit that a host clock is never read (finding 3 is about strengthening the proof, not a violation). **Standing order 12** — `VEC_CORR='NONE'` is quietly the correct call and I want it noted as a positive: geometric states in, light-time and aberration owned by the sim's causality filter, never smuggled into the ephemeris where they would be invisible to the invariant test. **Standing order 13** — tier fence holds; four bodies, patched-conic input only, n-body explicitly disclaimed per GDD §7.6, SPICE and tables deferred as future beads rather than built early. **Standing order 2** — the line 47-49 upgrade path makes the decision reversible and names the successor options. No pillar conflict. Nothing here needs Overseer escalation.

The rejections are reasoned, not hand-waved: SPICE is turned down on toolkit-platform reality and a 31 MB kernel, tables on unquantified interpolation and provenance cost, runtime Horizons on network dependence and replayability. Each names a specific cost rather than a preference. This is the standard I want spikes held to.
