## Findings

1. **No git remote exists — the workflow is dormant and has never run.** Severity: must-record (not a defect in the diff). `git remote -v` returns empty in both `/home/justin/dev/longburn-worktrees/c38` and `/home/justin/dev/longburn`. GitHub Actions has nowhere to fire. This is consistent with fort state, not a surprise: `fort/remember.md:3` records the GitHub org as unclaimed, and `longburn-8zw` (P1, deferred, HUMAN: Justin) is the bead that secures it. But it makes the handoff's next-action 2 — "close `longburn-c38` after approval **and a successful hosted workflow run**" — unachievable today. Standing order 6's distinction (committed ≠ pushed ≠ deployed) applies one rung further out here: written ≠ executed. Recommend closing c38 on the diff plus this review, with the bead recording explicitly that the workflow is unexecuted, and the first green hosted run tracked against `longburn-8zw` rather than blocking c38 indefinitely.

2. **CI institutionalizes an existing blind spot: the `test/` directory is checked by no verifier.** Severity: should-fix before T0 sim code. `tsconfig.json:14` includes only `src/**/*.ts`, and `tsc --noEmit --listFiles` confirms the type gate sees exactly six repo files, all under `src/sim/`. `package.json:8` lints only `src`. Vitest executes `test/` but transpiles via esbuild without typechecking. Proven by mutation on the scratchpad copy: I injected `const brokenTypes: number = "this is a string, not a number";` plus an unused local into `test/determinism-lint.test.ts` and ran all three CI verifiers — `npx tsc --noEmit` exit 0, `eslint src` exit 0, `vitest run` 7/7 green. A blatant type error and a lint violation in the fort's own determinism-guard file survive the entire pipeline. This is pre-existing (I filed it myself as findings 13 and 14 of the 8b5 round-2 review; it is beaded as `longburn-66g`, currently P3) and c38 did not introduce it. But c38 is the commit where `npm run verify`'s coverage stops being one seat's habit and becomes the institution's definition of "safe to merge," and the bead's own framing is that this fort never has an untrusted-verifier era. A gate that cannot see the file guarding standing orders 10 and 11 is a partly untrusted gate. Recommend promoting the tsc-coverage half of `longburn-66g` to P2 and landing it before `longburn-din.1`. (I hold no authority to file or re-prioritize beads; this is a recommendation to the Mayor.)

3. **Unfiltered `push:` alongside `pull_request:` will double-run every branch once a remote exists.** Severity: nit. `verify.yml:4-5`. Any push to a bead branch that also has a PR open fires both events, running the full suite twice. The conventional form is `push: { branches: [main] }` plus `pull_request:`, which keeps identical coverage and drops the duplicate. Costs nothing today; worth fixing in the same pass as findings 4 and 5. Note `refs/dolt/data` pushes do not trigger this — Actions fires push events only for `refs/heads/*` and `refs/tags/*` — so beads sync will not spuriously burn runners.

4. **No `concurrency` group and no `timeout-minutes`.** Severity: nit. A superseded push keeps burning a runner to completion, and a hung vitest occupies one for the 6-hour default. `concurrency: { group: "${{ github.workflow }}-${{ github.ref }}", cancel-in-progress: true }` at workflow level and `timeout-minutes: 10` on the job are the standard pair.

5. **Node is pinned in CI but nowhere in the repo, and CI's version differs from the fort's machine.** Severity: should-fix. `verify.yml:17` pins `node-version: 22`; the machine running the Forge and this review is on v24.14.0 (npm 11.9.0). No `engines` field, no `.nvmrc`, no `.node-version` is tracked. So "verifiers green locally" and "CI green" are two claims about two different runtimes, and nothing in the repo says which one is authoritative. This is build toolchain, not sim core, so standing orders 10 and 11 do not literally reach it — but a fort whose charter makes reproducibility law should declare its runtime in one place. Add `.nvmrc` plus an `engines` field and switch the workflow to `node-version-file: .nvmrc`, so the pin has exactly one definition.

6. **CI restates `npm run verify` instead of calling it.** Severity: nit, advisory only. `package.json:10` defines `verify` as `lint && build && test`, where `build` is `tsc --noEmit`. The workflow runs the same three checks by other names (`npx tsc --noEmit` rather than `npm run build`). Same set, two definitions — a fourth verifier added to `verify` later (the causality suite, `longburn-6yu`) would silently not run in CI. Against that, the split steps give better failure attribution in the Actions UI, which is worth something. The bead's description literally specified `npx tsc --noEmit`, so the Forge followed spec and I am not counting this against them. My preference is to keep the separate steps but source them from the npm scripts, so `verify` stays the single definition of the word.

## Action pinning

`actions/checkout@v4` and `actions/setup-node@v4` are floating major tags, not commit SHAs. For a private repo with `permissions: contents: read` and no secrets in the workflow, major-tag pinning is the normal bar and full-SHA pinning is the paranoid tier. I am not asking for SHAs now. Revisit if this workflow ever gains write permissions or touches a secret — at that point tag mutability becomes a real supply-chain surface rather than a theoretical one.

## What surprised me

`package-lock.json` carries `"name": "8b5"` at top level — the directory name of the *previous* bead's worktree — while `package.json` is `"longburn"`. It is harmless: the lock's `packages[""]` entry has no `name` or `version` key at all, so `npm ci` has nothing to compare and does not complain (confirmed by the harness's clean `npm ci`). Cosmetic, inherited from 8b5, not c38's to fix. Worth knowing before someone reads the lockfile in a dispute and concludes the tree was assembled from the wrong package.

The other surprise was pleasant. `eslint.config.mjs:8` scopes the determinism rules to `src/sim/**` *and* `test/fixtures/sim/**`, while `npm run lint` only passes `src` — which reads like a bug until you see `test/determinism-lint.test.ts` drive ESLint through the Node API over that fixture deliberately. The negative fixture is kept out of the default lint run on purpose, so `verify` is not permanently red. That is the right structure, and it is the reason finding 2 is a typecheck gap rather than a lint gap.
